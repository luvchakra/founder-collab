# E2E Coverage Gaps

What was **not** genuinely tested in the 2026-10-01 validation, and why. Nothing listed here
is reported as passed anywhere else.

| # | Feature | Reason not tested | Risk | What testing it requires | Recommended next action |
|---|---|---|---|---|---|
| G-01 | Firefox and WebKit | Only Chromium is installed in the sandbox the suite was built in; this environment forbids `playwright install` | Medium -- Safari-specific layout/date-input/cookie quirks are invisible | `npx playwright install firefox webkit`, then `E2E_BROWSERS=firefox,webkit` (projects `smoke-firefox`, `smoke-webkit` already exist) | Add the install + flag to the CI `e2e` job once it is enabled |
| G-02 | Real payment flows (Stripe / Razorpay checkout → provider → signed webhook → licence) | No provider sandbox keys or webhook secrets are configured on dev (`/api/webhooks/billing/stripe` answers 503 "not configured"); a real signed delivery can't be produced without them | **High** -- licence activation is a money path | Sandbox keys + webhook secret on a dedicated test project, then deliver test-mode events (success, failure, duplicate, replayed, delayed, out-of-order, cancellation, renewal, expiry) | Covered today only by unit tests (`packages/core/src/billing/*.test.ts`) and the refusal paths in SEC-HTTP-02/03; build a signed-webhook replay suite with sandbox keys |
| G-03 | Cron jobs' success paths (drain events, expire licences, reminders, recurring entries, escalation…) | A valid `CRON_SECRET` call would act on **every real tenant** on the shared dev project (send email, post entries) | Medium | An isolated project with only fixture tenants, or a tenant filter on the handlers | Run against a Supabase branch / local stack; refusal paths are covered (SEC-HTTP-01) and DB logic by `test:db` |
| G-04 | Live AI generation (offering discovery, ICP, research, outreach drafts, reply classification, chat, CRM summaries) | No provider key configured for the dev project in this run; live calls are slow, cost money and are non-deterministic | Medium | A provider key + a recorded-response (fixture) mode, or a cheap model under a budget | Prompt-injection fencing is unit-tested (`injection.test.ts`); malformed/empty/timeout/provider-error handling is in the modules' vitest suites. Add an E2E with a stubbed provider endpoint |
| G-05 | Inbound channels end to end (email-inbound, WhatsApp, Meta, Resend status) with *valid* signatures | Secrets not configured on dev; real deliveries would hit real tenants' data | Medium | Test secrets + a fixture-only project | Only forged/unsigned refusals are covered (SEC-HTTP-02) |
| G-06 | Platform-admin happy paths (plans, modules kill switch, billing ops, AI routing, branding publish, compliance packs, announcements) | The only platform admin on dev is a real person; creating a superadmin fixture means writing `platform.admins` on a shared control plane | Medium -- the refusal side (SEC-PLAT) is covered, the working side isn't | A fixture superadmin with a TOTP factor on an isolated project | Add a `platformAdmin` identity to the fixtures on a dedicated project; the TOTP helper in `cross-tenant-ui.spec.ts` already exists |
| G-07 | Invitation acceptance through email links | Sending invites emails a real address; Resend isn't configured | Low-Medium | Mail sink (e.g. Resend test mode) | DB-level acceptance is covered by `scripts/test-core-rbac-rls.mjs` |
| G-08 | Exhaustive CRUD/sort/filter/paginate per module page | ~93 of 196 routes are smoke-visited or not visited by URL at all (see the inventory appendix); a full matrix is weeks of work | Medium | Per-module journey specs | Prioritise Inventory (orders → invoices → returns) and Finance (journal → statements) journeys next |
| G-09 | Large datasets (exports of 10k+ rows, pagination limits, background export jobs) | Seeding large volumes into the shared dev project is not appropriate | Low-Medium | Isolated project + bulk seed | Add once a branch/local stack is available |
| G-10 | Concurrency (double submit, parallel number allocation, duplicate webhook race) at the E2E layer | Not built in this pass | Low -- `core.next_number` concurrency and idempotency keys have DB tests | Parallel request harness | Extend SEC-HTTP with concurrent duplicate submissions |
| G-11 | Session expiry by time (an hour-old token) | Would need clock control or waiting out token lifetime | Low -- tampered/cleared cookies are covered (AUTH-02/03) | Short JWT expiry on a test project | Configure a 60 s JWT expiry on a test project |
| G-12 | Contrast and screen-reader semantics beyond the smoke checks | No axe-core dependency (not added: "no new dependency unless necessary") | Low-Medium | `@axe-core/playwright` | Decide whether to adopt axe-core; the current smoke catches labels, names, alts, headings, overflow |
| G-13 | Production environment | Out of scope by instruction; never tested against production | -- | -- | Check production for the migration drift found on dev (E2E-DEF-008) |
| G-14 | E2E-DEF-011 root cause | Not reproducible in reruns | Medium | Load re-run with server-side error logging | See E2E_DEFECTS.md |
| G-15 | Exhaustive abuse of `SECURITY DEFINER` RPCs | SEC-TI sweeps every *relation* automatically, but RPCs only by sample (`has_permission`, `effective_permissions`, `my_business_access`, `next_number`). A parallel session's review found `core.write_audit_log()` accepting forged cross-tenant writes (fixed on `main` as SEC-2) -- exactly this class | **High** -- a definer function bypasses RLS by design | Enumerate every function granted to `authenticated` and call each with tenant B's ids as tenant A, asserting refusal or no foreign effect | Build an RPC sweep alongside SEC-TI-01 (function list from `pg_proc` / PostgREST's OpenAPI `rpc/` paths) |
